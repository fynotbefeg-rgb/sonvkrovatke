# Один процесс сейчас без ноутбука и позже с Windows

Дата: 2026-10-10. Ноутбук недоступен и первичная настройка невозможна. Это не блокирует разработку очереди, бота и монтажа. Авторизация Claude Code и реальные вызовы сервисов остаются отдельными шагами.

## Реализованное ядро

`scripts/production-queue.mjs` хранит tickets, jobs и callbacks в SQLite (Node ≥22.13). `scripts/telegram-start-controller.mjs` связывает проверенное Telegram-событие с очередью. Это **ядро без сетевого transport и без развёрнутого бота**; создание очереди не вызывает HeyGen, Drive или рендер.

Общий production_key = SHA-256 JSON.stringify([version_id, revision, script_hash]). Он создаётся до получения видео. Это другой ключ, чем intake job_key, который дополнительно связывает конкретный MP4 и MD5. После получения видео нужно сохранить связь между ними, не подменять один другим.

Два обработчика этапа аватара:

| Provider | Сейчас / позже | Состояние задания |
|---|---|---|
| `manual_upload` | Сейчас: человек создаёт речь в HeyGen и загружает цельный MP4 | `waiting_for_manual_upload` |
| `windows_browser` | Позже: локальный worker Windows управляет обычным интерфейсом HeyGen | `waiting_for_windows_worker` |

Пока оба состояния только ожидание: Windows worker не реализован, очередь не нажимает Generate. Нет HeyGen API. Для ручного этапа задание содержит точный утверждённый полный текст и ожидаемое имя MP4 по существующему intake-контракту. В speech уже может входить хук; не добавлять его второй раз.

## Защита кнопки

Сервер создаёт короткую кнопку `start:<ticket_id>` только для выбранных **утверждённых** вариантов. Ticket фиксирует production_key каждого выбранного сценария/хука, разрешённого оператора и срок действия (обычно 15 минут). Полный текст/секреты не помещаются в callback.

Контроллер принимает только личный чат разрешённого Telegram ID. ID автора/username — не новый Google receipt; контроллер не утверждает ничего за Романа. При обработке кнопки `readCurrentApprovals()` читает **текущий аутентифицированный источник**, а не `approvals` или `provider` из Telegram JSON. Изменённый/отозванный сценарий, неутверждённый хук или недоступный approval-сервис блокируют запуск. В текущей версии источником должен быть проверенный Google receipt/queue; прямое утверждение Telegram пока не реализовано.

**Граница transport:** `handleVerifiedStart` нельзя публиковать как HTTP endpoint, доверяющий произвольному JSON с `from.id`. Будущий webhook-адаптер обязан сначала проверить Telegram webhook secret/контекст доставки. Настоящие sender ID берутся из проверенного события, список операторов — только из конфигурации сервера. Для long polling нужна серверная авторизация Bot API. Ни bot token, ни transport secret не хранить в callback, Git или чате.

SQLite BEGIN IMMEDIATE и уникальный production_key не допускают две записи для одной утверждённой версии. Повторная доставка, двойной клик и новая кнопка к той же версии не создают второе задание. Изменённый callback_id с тем же ticket тоже безопасен; коллизия ID для другого ticket отклоняется. Запуск пакета атомарный: если один вариант отозван, новые задания пакета не создаются.

## Переход к ноутбуку

Для ещё ожидающего задания `switchWaitingProvider(key, 'windows_browser')` сохраняет production_key, текст, hash и имя исходника. Повторная старая кнопка не переводит его обратно в manual. Не надо заново утверждать **неизменённый** текст только ради смены исполнителя, но будущий worker обязательно повторно проверяет действующее утверждение перед действиями.

Switch меняет лишь ожидающий статус; **не запускает** браузер и не разрешает расходы. Готовое/выполняющееся задание нельзя просто перенаправить и генерировать повторно. Для дальнейших стадий ещё требуются atomic claim/lease, переходы состояния, учёт уже созданного проекта HeyGen и проверка результата.

## Хранение и ограничения

Использовать постоянный приватный путь, например `roman-reels/runtime/production.sqlite`; runtime исключён из Git. Настроить доступ к каталогу/базе только серверному пользователю и резервную копию. База содержит полные утверждённые тексты, поэтому её нельзя загружать публичным artifact.

SQLite этой реализации рассчитан на один постоянно доступный coordinator host. Файл на одноразовом runner GitHub Actions или artifact не является постоянной производственной очередью. Для нескольких хостов понадобится подходящее транзакционное хранилище; не синхронизировать SQLite через Drive.

Очередь пока не выдаёт lease обработчику, не принимает/скачивает MP4, не валидирует реальную речь, не транскрибирует, не запускает Remotion и не обновляет статус в Google. Все возвращаемые задания имеют `generation_started:false`, `render_allowed:false`. Локально пройденные тесты не доказывают авторизацию Telegram/Google или готовность worker.

Проверки:

```bash
node roman-reels/scripts/production-queue.test.mjs
node roman-reels/scripts/manual-intake.test.mjs
```

12 новых проверок: привязка текста, запрет pending/чужого хука, повторная доставка, чужой оператор/группа, spoofed approvals, срок/владелец кнопки, смена текста/хука/ревизии, атомарность пакета, смена provider без дубля, ошибка approval-read, коллизия callback и восстановление SQLite после перезапуска. Fixtures тестовые, они не утверждают реальные пилоты. Дополнительно восемь существующих intake-тестов проходят.

Ручной workflow `roman-reels-check.yml` с `test_production_queue=true` проверяет это offline на Node22, без секретов, без Gemini/Apify/Claude/HeyGen и без подключения к реальному Telegram.
