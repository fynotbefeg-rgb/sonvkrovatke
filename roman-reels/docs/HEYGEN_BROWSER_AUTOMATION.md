# HeyGen без API — проект Windows-исполнителя

Статус: архитектура, **реальная автоматизация не реализована и не разрешена к запуску**.
API HeyGen не используется. Ноутбук сейчас недоступен; облачная разработка не зависит от него.

на странице указано Last Updated July 23, 2026. Раздел 2 содержит ограничения на стороннюю
автоматизацию и автоматизированный доступ/сбор данных, а также обход технической защиты.
Это не подтверждение разрешения Playwright для создания, наблюдения и скачивания видео.
В терминах отдельно рассматривается пользовательский контент; из этого нельзя вывести
автоматическое разрешение выбранного браузерного workflow.

Текущий gate: `policy_permission_required`. До реальной реализации необходимы явное допустимое
основание для конкретного сценария (например, письменное подтверждение HeyGen для аккаунта)
и проверка актуальных правил непосредственно перед тестом. Согласие владельца не заменяет условия сервиса.
Не запускаем обход CAPTCHA/anti-bot/login/2FA, не вызываем скрытые backend endpoints вместо UI.
Если разрешения нет, фиксируем блокер выбранной схемы; допустимый резерв — ручная генерация/экспорт
пользователем и единый Drive intake. API не включать как незаметную замену.

## Архитектура после разрешения

Cloud сохраняет задания и состояния; Windows инициирует HTTPS outbound polling,
не принимает публичные порты. Один worker, один job одновременно. Playwright — кандидат,
окончательный выбор после разрешения и проверки UI. Локальный headed browser profile
с пользовательской авторизацией; профиль/cookies/пароль не попадают в GitHub или Actions artifacts.

Перед claim/submit: свежий authenticated snapshot утверждения, точные revision/hash/text,
разрешённый avatar ID/consent, настройки и согласованный бюджет одной генерации.
Текст вставляется дословно; preview сверяется с snapshot. Сеть/таймер — не доказательство успеха.
Не запускать генерацию пока ограничения аккаунта, credits и порядок подтверждения не проверены.

## Состояния и восстановление

Предлагается добавить к существующей очереди leases, heartbeat, worker identity и fencing token.
Transitions: waiting_for_windows_worker → leased → prepared → submit_intent_saved →
submitted(projectId) → generating → downloaded → drive_registered → source_ready.
Ветка manual_attention: auth_required / challenge / policy_blocked / ambiguous_submission.
Каждый transition транзакционен, сохраняет production_key и историю без секретов.

До Generate сохранить intent. Если процесс оборвался во время клика, не считать lease expiry
разрешением повторно нажать Generate. Возобновить по известному project ID; если он неизвестен,
manual reconciliation в разрешённом UI. Система не гарантирует exactly-once внешний клик без
идемпотентности сервиса; гарантирует отказ от слепого повторного платного действия.
Если approval отозван после submit, сохранять возникший project для reconciliation, но блокировать
дальнейшую обработку/публикацию по устаревшему тексту.

Скачивание: временный файл → ffprobe + полный decode → checksum → атомарное переименование
в `<reelId>__r<revision>__<scriptHash>.mp4` → загрузка в проверенную incoming folder.
Drive file ID/checksum + approval snapshot регистрируются в общем intake.
При сбое upload повторять загрузку только после поиска уже зарегистрированного результата.
При недоступном ноутбуке задания остаются cloud waiting; уже принятые MP4 работают в облаке.

## Проверки до подключения реального аккаунта

Mocks: выключенный worker, reboot, lease expiry, два worker, stale hash, отзыв approval,
потеря сети до/после submit, missing project ID, expired login, CAPTCHA→pause, download corruption,
duplicate upload, смена manual→Windows без нового заказа. Сейчас эти worker-тесты ещё не реализованы.
После разрешения и настройки — один ограниченный тест с просмотром результата, затем оценка лимитов;
никакой массовой генерации до него.
