# Исследование: ИИ-проверка сайта шире одной кнопки

Проверено по актуальным официальным страницам 2026-10-10. Предложение темы,
не утверждённая речь. Новый аудит и подключённая сессия Claude не запускались.

## Вывод для темы

Замечание Романа меняет масштаб: проверять ключевые пути сайта и фиксировать
покрытие, а не делать установку MCP или одну кнопку главным результатом.
Предлагаемый угол: «ИИ проверяет сайт как клиент и оставляет повторяемые
тесты: страницы → сценарии → ошибки с доказательствами → повтор после правок».
Это редакторский вывод, а не доказанный успех нашего нового эксперимента.

«Проверить весь сайт» нужно раскрывать как перечисленный объём проверок.
Обход ссылок не покрывает все состояния, роли, формы и бизнес-правила.
Отчёт должен показывать проверено / ошибка / заблокировано / не проверено,
а не утверждать отсутствие любых ошибок.

## Подключается ли Playwright автоматически

- В Claude Code MCP из включённого плагина запускается автоматически.
  Это не значит, что любой Playwright установлен во всех сеансах по умолчанию.
  Источник: https://code.claude.com/docs/en/mcp (Plugin-provided MCP servers).
- Текущая инструкция Playwright MCP требует добавления сервера в клиент;
  браузер скачивается автоматически при первом использовании. Сейчас
  страница указывает Node.js 20+. Старый проверенный @playwright/mcp@0.0.83
  остаётся историческим тестом, а не утверждением о текущих требованиях latest.
  Источник: https://playwright.dev/mcp/installation
- Claude Code также имеет отдельную интеграцию Claude in Chrome. Нужны
  расширение, подходящая подписка/вход и включение интеграции; предусмотрено
  Enabled by default. Это отдельный путь, не Playwright MCP. Наличие браузера
  в облачной среде Codex не доказывает его наличие в сеансе Claude владельца.
  Источник: https://code.claude.com/docs/en/chrome

По доступным файлам репозитория нельзя установить конфигурацию отдельного
сеанса Романа/владельца. Если там браузер уже работает, повторная установка
не нужна. В будущей демонстрации сначала определять доступный инструмент.

## Какие варианты актуальны

Playwright CLI + skills: официальный вариант для coding agents; документация
предпочитает его для экономного использования контекста, MCP — для длительных
диалоговых обходов с состоянием. Это рекомендация разработчика, не измеренная
нами экономия. Источник: https://playwright.dev/docs/getting-started-cli

Playwright Test Agents: planner исследует приложение и составляет план,
generator создаёт тесты, healer помогает чинить упавшие тесты. Для Claude
даны определения через npx playwright init-agents --loop=claude; нужен
подготовленный проект/seed test. Healer способен пропустить тест, если считает
функцию сломанной: это не исправление продукта и не успешная проверка.
Источник: https://playwright.dev/docs/test-agents

Для демонстрации разумно сравнить разовый осмотр браузером с сохранёнными
Playwright-тестами. Выбор CLI/MCP определяется доступной средой, а не названием
ролика. Новые пакеты, агенты и платная Claude-сессия здесь не запускались.

## Может ли хватить одного промпта

Один запрос может задать ИИ весь рабочий процесс после подготовки браузера,
доступов, тестовых данных и ожидаемых результатов. Внутри будут многие
действия, запуски и проверки. Официальные примеры подтверждают запуск задач
естественным языком, но не гарантию полного аудита произвольного сайта.
Практическая проверка «один запрос → наш результат» ещё предстоит.

research/mcp-site-audit-current/site-audit-prompt.md — подготовленный запрос,
не исполненная сессия. Он требует карту покрытия и воспроизводимые сценарии.
Для регулярного контроля после обновлений нужен отдельный запуск тестов/CI.

## Что включить в содержательную демонстрацию

На собственном учебном сайте проверить несколько страниц и типов действий:
меню/переходы, загрузку ресурсов, мобильное меню/раскладку, валидацию формы,
контролируемую отправку в учебный приёмник. Для последнего недостаточно
уведомления «успешно»: нужна запись приёмника, связанная с тестовой заявкой.
Это наш план эксперимента, не уже проверенные возможности клиентского сайта.

Артефакты: список страниц и сценариев, шаги воспроизведения ошибки, скриншоты,
ожидаемый/фактический результат, сохранённые тесты и повтор до/после правки.
Для браузеров/мобильных конфигураций предусмотрены Playwright projects:
https://playwright.dev/docs/test-projects ; отчёты:
https://playwright.dev/docs/test-reporters

Доступность можно расширить axe-проверками, но автоматические проверки
находят только часть проблем. Это не полный WCAG-аудит. Источник:
https://playwright.dev/docs/accessibility-testing

Проверку скорости, безопасности, SEO, платежей и настоящей доставки в CRM
не включать как якобы выполненную; для каждой нужны отдельные критерии,
инструменты/доступы и доказательства. Мобильная эмуляция не равна тесту
на настоящем iPhone. Не обещать рост продаж по результату технических тестов.

## Следующий этап

Подготовить многосценарный учебный сайт с известными дефектами. Измерить,
какие из них находятся, какие пропускаются, и сохраняются ли полезные тесты.
Лишь после результата — Gemini: новая основа и три хука, затем утверждение
точной речи. MCP v3 остаётся историческим pending-пакетом; его текст/хеши
не менялись и новая речь его утверждение не наследует. Популярный внешний
референс именно для расширенного угла пока не проверен.
