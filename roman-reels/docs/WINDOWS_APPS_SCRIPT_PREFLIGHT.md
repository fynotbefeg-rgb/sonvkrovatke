# Claude Code на Windows: проверить живой Apps Script перед внедрением

Задание 2026-10-12. Цель — выяснить реальную совместимость нового topic reader с текущим Apps Script, не развёртывать код и не менять решения Романа. Эта проверка может выполняться параллельно с облачной разработкой topic-first регистрации.

## Действия

1. В существующем клоне проверить origin, ветку и отслеживаемые изменения; git fetch origin. Документы читать через git show origin/feature/codex-pipeline:roman-reels/docs/... без reset/clean/force и без перезаписи локальных файлов. Прочитать TOPIC_SELECTION_READER.md, SHARED_REVIEW_BRIDGE.md и этот документ. Node уже установлен, ничего не устанавливать.
2. Проверить настоящие MCP-инструменты текущей сессии. Только через них открыть наш существующий Apps Script:
https://script.google.com/d/1XxdsdAGLMf1IY15812fwW5EQp6MJoCgDm7J96H10h0xk_Hykd_utvnd1/edit
Не менять headless/isolated/профиль MCP, не искать или переносить cookies из другого браузера. Если появляется вход Google/нет доступа/сессия MCP недоступна — вернуть точный блокер и требуемое одно действие владельца. Не вводить пароль, не выбирать чужой аккаунт и не менять sharing/OAuth самостоятельно. Проверка уже полезна как установление отсутствующего доступа; не придумывать остальные результаты.
3. Если авторизованный доступ существует, проверить проект, видимые имена файлов, доступность просмотра кода и deployments. Не открывать Script Properties: там могут отображаться токены. Не выводить исходный код целиком, значения секретов, browser cookies или сетевые Authorization-заголовки. Не сохранять публичные скриншоты аккаунта/редактора.
4. Если можно безопасно получить код без вывода секретов, сохранить резервную копию вне Git в LOCALAPPDATA/RomanReels/apps-script-backup/<timestamp> и сверить только структурные признаки: Code.gs/RomanApproval.gs/SharedReview.gs, число действующих doPost/onRomanApprovalEdit, наличие e.user проверки, authenticated POST actions, текущая поддержка shared review/topicSnapshot. Сохранение исходного кода — только локально, без вывода в stdout/логи/PR. Если инструменты не позволяют безопасный экспорт, отметить backup unavailable; не подменять резервную копию файлами из репозитория.
5. По доступным данным составить короткий отчёт: аккаунт имеет/не имеет доступ (без адреса почты), имена файлов и обработчиков, какая схема установки фактически используется, существует ли поддержка нового action, создан ли private backup, нужны ли дополнительный файл/правка/новая версия существующего deployment. Не выдавать названия функций за доказательство корректности реализации; отдельно указать, что не удалось проверить. Не менять код, deployments, triggers, таблицу, feature flags или токен.
6. Отчёт должен прямо разделять: зарегистрированные shared темы (для reader) и отсутствующую topic-only регистрацию до основы/хуков. Не пытаться создать пустые/фиктивные body/hooks или импортировать прежние решения как новые подтверждения.

## Передача отчёта без ручного копирования владельцем

Создать отдельный worktree/ветку feature/windows-apps-script-audit-20261012 от актуальной origin/feature/codex-pipeline, сохранив основной клон и все старые файлы. Добавить только безопасный Markdown-отчёт roman-reels/docs/WINDOWS_APPS_SCRIPT_AUDIT_RESULT.md; никаких исходников живого проекта, логов, токенов, личных путей/почты или резервных копий. Commit, push с существующей GitHub-авторизацией; перед созданием PR проверить дубликат. PR в feature/codex-pipeline, без reviewers/слияния/main. Установка gh не нужна: существующая разрешённая API-авторизация либо branch push и ссылку верни владельцу — Codex создаст PR из своей среды.

Оригинальный private backup, если удалось создать, остаётся локально. В отчёте можно указать наличие/число файлов/SHA256, но не их секретное содержимое. Даже при отсутствии Google-доступа сохранить полезный отчёт о конкретном блокере. Если нет прав на push — сохранить локальный результат и вернуть точную ошибку.
