# Меньше доработок Романом: проверка перед отправкой

2026-10-11. Это проверка готовности показать черновик, не утверждение и не
запуск производства. Live Apps Script и таблица не менялись.

## Причина разрыва

До изменения send-drafts-to-sheet.mjs требовал только pending_approval и
правильное число записей. Завершённая редакторская проверка не была условием
сети/отправки. Дополнительно v6-бриф прямо требовал описать подготовленный,
но ещё не испытанный Claude-промпт. Gemini не мог показать проверенный
результат этой инструкции, поэтому основа осталась преимущественно чек-листом.
Это недостаток материала и связи этапов; смена модели сама его не исправляет.

## Новый порядок

1. Исследовать конкретный процесс для бизнеса, выбрать доступный релевантный
   внешний ролик. Для новой практической темы: до 60 дней, не менее 100 тыс.
   source-verified public views/plays, актуальный срез до 7 дней. Это начальный
   фильтр, не доказательство вирусности/причин успеха или будущих просмотров.
2. Проверить предлагаемую инструкцию, записать вход, действия, результат,
   способ перепроверки и ограничения. Не заменять реальный Claude/MCP/n8n
   опыт заранее написанным тестом другого инструмента. Учебный кейс допустим,
   если он испытан в указанной связке и это раскрыто.
3. Только с достаточными данными готовить бриф Gemini. Если их нет — вернуть
   исследование на доработку, не создавать очередные общие формулировки.
4. Проверить факты/полезность/смысл хуков отдельно, заполнить восемь редакторских
   критериев с пояснениями и доказательствами. Это работа редактора/Codex,
   а не дополнительная работа Романа. Код не умеет доказывать смысл текста.
5. Выполнить editorial release preflight для точных трёх полных сценариев.
   Передать Роману один компактный пакет с внешним примером, основой, хуками
   и коротким объяснением пользы. Решение Романа остаётся отдельным этапом.

## Исполняемые компоненты

- editorial-release.mjs: проверяет текущие speech hashes, общую основу,
  актуальную версию правил, задачу/пользу, доступный прямой URL, дату/счётчики
  в сохранённом артефакте, hashes доказательств, завершённые критерии.
- check-editorial-release.mjs: read-only отчёт. При блокировке сохраняет
  конкретные причины и возвращает exit code 2; модель/Google не вызываются.
- send-drafts-to-sheet.mjs: второй обязательный аргумент — завершённая проверка;
  ошибка до чтения webhook configuration/сетевого запроса. Старый вызов с одним
  аргументом блокируется, даже если все записи pending_approval.
- send-shared-review.mjs: тот же контроль перед add_shared_review; единственный
  POST, без повторов. Сохраняет решения пустыми. На mock проверена регистрация
  ровно одной основы и трёх хуков. В live не запускался; SharedReview ещё не установлен.

Для этой версии release sender поддерживает один исследованный topic, три
варианта без окончаний. Отдельная редакционная привязка шести платформенных
полных текстов к проверке окончаний ещё не реализована; не подменять проверку
всех шести отчётом только по базовым трём. Offline prepare-shared-review по-прежнему
поддерживает 3/6, но это не право отправки или утверждения.

Критерии: task/reference/setup/demo/claims/costs_limits/body_hooks/approval.
Каждому нужны pass, пояснение и ссылка на доказательство. Отдельно reviewer,
semanticReviewCompleted=true, romanApprovalGranted=false. Review связан с
current legacy scriptHash всех трёх версий и хешем правил 1.1.0. Подмена текста
после проверки, устаревшие доказательства или pending блокируют отправку.

Счётчик берётся из primaryCounters или primaryEmbed.videoViewCount сохранённого
research JSON, агрегатор отдельно не проходит. Отчёт инспектора должен иметь
реальное происхождение: сам JSON/хеш не доказывает подлинность данных сервиса.
Ограничения кода: это проверки формы и declared evidence; отдельная честная
проверка источников и смысла по-прежнему необходима. Не ставить true/pass,
чтобы лишь разблокировать отправку. Артефакты читаются только в research,
проверяются hash, symlinks и лимит 2 MiB. Никаких credentials в них не сохранять.

## Стоимость: обязательный costReview (правила 1.2.0)

Требования Романа ведутся в CONTENT_REQUIREMENTS.md. Отправители блокируют отсутствие проверенного бесплатного пути для зрителя. Протокол содержит `costReview`: `status: verified`, `scope: viewer_workflow`, `workflowMatchesScript: true` и `evidence: {path, sha256}` на JSON в research.

Артефакт стоимости: `scope: viewer_workflow`, `requiredPayment: false`, `trialOnly: false`, непустые `testedUsage`, `limitations`, массив `components`. Покрыть все слои `tool`, `model`, `integration`, `execution`, `data`, включая все обязательные зависимости каждого слоя. Для каждого: `layer`, `name`, `access` (free/free_tier/not_required), `requiredPayment: false`, `requiredCost: 0`, `checkedAt`, `limits`, `sourceUrl` (официальный HTTPS источник), `sourceQuote`. Для not_required дополнительно `notRequiredReason`. Тарифы проверяются не более 30 дней назад. При любом неизвестном/платном/просроченном компоненте отправка запрещена.

Цитаты, полноту списка зависимостей, официальность URL и соответствие теста проверяет редактор: автоматическая структура и хеш не подтверждают их истинность. Учебные example.com данные существуют только в тестах, не являются доказательствами стоимости реальных сервисов. Платная подписка Claude Pro/Max не превращается в бесплатную из-за того, что она уже куплена.
