# Применение редакторских правил

Подготовлено 2026-10-10. Пока Роман не выбрал темы из новой подборки,
новые сценарии по ним не генерируем. Исследования и учебные тесты допустимы.

## Что подключено

GEMINI_EDITORIAL_RULES.md — единый текст правил версии 1.0.0. Модуль
scripts/editorial-rules.mjs загружает этот файл, считает SHA-256 и создаёт
независимый pending-чек-лист. researchPrompt из researched-gemini-drafts.mjs
вставляет правила перед данными брифа. Факты и инструкции внешних источников
не могут менять эти правила. Изменение правил меняет их SHA-256; существенную
смену требований сопровождать обновлением версии в модуле и этом документе.

Результат researchedDrafts получает editorialReview: pending_review, восемь
пунктов pending, без проверяющего и решения. Поля от модели и metadata не
могут утверждать этот отдельный чек-лист. Речь остаётся pending_approval;
productionReady=false. Это не новая система утверждений: действующий
механизм проверки версии и хеша текста сохраняется.

## Порядок работы после выбора

1. Codex проверяет актуальный выбор Романа, фиксирует источник решения
   и узкую задачу. Выбор темы не считается утверждением будущей речи.
2. Проверяет внешний референс, происхождение статистики, официальные
   технические документы и необходимые доступы. Пробелы явно записывает.
3. Выполняет собственный узкий тест с учебными данными, сохраняет вход,
   хеш и результат. Незавершённый шаг не описывает как работающий.
4. Готовит исследовательский briefVersion 1.0.0 по существующему формату:
   topicId, scriptRevision (не ниже 2 в текущем адаптере), businessProblem,
   romanFeedback, sources, alternatives, demo, requirements. В requirements
   указывает факт/источник выбора темы, настройки, стоимость и границы.
   Адаптер пока предназначен для исследованных редакций с synthetic demo;
   новые типы доказательств требуют отдельного расширения контракта.
5. Сначала запускает локальный prepare; проверяет сформированный запрос.
   generate запускает отдельно только для готового брифа в рамках
   согласованных расходов. Наличие preview не является разрешением платежа.
6. Gemini создаёт одну основу и три хука или insufficient_evidence.
   Автоматическая валидация не оценивает истинность и полезность текста.
7. Codex заполняет копию editorialReview: pass / revise / blocked с
   обоснованиями и источниками. Любой revise/blocked/pending означает,
   что редакторская проверка ещё не завершена. При правках сохраняет
   происхождение Gemini/Codex и пересчитывает хеши существующими средствами.
8. Роману предлагается точная речь с тремя хуками. Производство возможно
   только после отдельного утверждения её актуальной версии и хеша.

Автоматической проверки решения Романа по новой подборке, редакторского
pass/blocked и автоматического возврата текста в Gemini пока нет. Эти шаги
выполняет Codex. Pending-чек-лист документирует проверки, но не заменяет
производственный approval gate. Новые темы не активированы в scanner.

## Подготовка без API

Из корня репозитория (output должен отсутствовать):

```bash
node roman-reels/scripts/run-researched-gemini.mjs prepare \
  roman-reels/research/mcp-site-check/brief-revision3.json \
  /tmp/roman-editorial-preview.json
```

Это исторический MCP-бриф для проверки интеграции правил, а не генерация
по новой теме. Локальный prepare не читает API-ключ и не делает сетевых
запросов. Preview содержит prompt, версию/хеш правил и pending-флаги.
Ничего в Google Sheets/Drive/HeyGen не записывает.

GitHub режим prepare_research дополнительно выполняет проверку каталога
моделей GET; он не является полностью офлайн. legacy_smoke использует
старый общий генератор и может отправлять тестовые черновики в Sheets:
он не подключён к этим правилам и не подходит для нового редакторского
процесса. Не использовать его для текущей подборки.

Текущий workflow выбирает только исторические seo/mcp_site брифы.
Новые выбранные темы подключаются отдельно после исследования; сейчас
не добавлены в автоматический запуск. Не запускать массовую генерацию
или перегенерацию текущей pending-речи только из-за изменения правил.
