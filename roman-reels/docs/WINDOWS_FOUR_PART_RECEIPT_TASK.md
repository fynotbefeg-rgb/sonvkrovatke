# Следующее задание Claude: квитанция после четырёх загрузок

Цель: дополнить загрузчик PR22, а не управлять HeyGen. Работа в отдельной
ветке/worktree, результат PR в feature/codex-pipeline без слияния/main.

Прочитать PR23, FOUR_PART_DRIVE_INTAKE.md и build-four-part-receipt.mjs.
PR22/23 не слиты: зависимость должна быть явно указана; не сливать их самому.

1. Взять функцию генератора квитанции из PR23. Вход — явный проверенный
   четырёхчастный пакет и локальный журнал загрузчика. Не присваивать
   textHash задним числом старым загрузкам. Если пакета нет, сообщить блокер,
   не брать старые отклонённые основы и не менять утверждения Романа.
2. После четырёх verified uploads создать квитанцию существующего receipt v1.
   До отправки заново проверить реальные Drive ID/роли/папку/размер/MD5/SHA
   всех четырёх файлов. Локальный журнал сам по себе не подтверждает Drive.
3. Добавить отдельную JSON-загрузку recording-set.json, не выдавать её за MP4.
   Квитанция появляется под окончательным именем только после верификации.
   Сохранить зарезервированный Drive ID до записи; после неоднозначного
   сбоя искать по этому ID. Повтор после перезапуска не создаёт дубль,
   чужая/изменённая существующая квитанция блокирует, не перезаписывается.
4. Не менять облачный intake-state, не удалять исходники/тестовую папку,
   не включать автозапуск и не запускать реальное производство/HeyGen.
5. Автономные тесты: неполный комплект, неверный/отсутствующий textHash,
   изменение Drive-файла, checksum квитанции, потеря ответа, повтор новым
   процессом, конфликт квитанции, отказ авторизации. Без платных вызовов.
6. Пока подготовить код/тесты. Полный живой четырёхчастный прогон выполняется
   следующим отдельным ограниченным этапом с явным synthetic-пакетом;
   он никогда не становится утверждённой речью или production-видео.

Ответ ≤4 строки: результат, PR, проверки/блокер, одно действие владельца.
