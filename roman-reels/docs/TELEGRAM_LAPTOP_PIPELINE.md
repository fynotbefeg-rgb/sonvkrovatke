# Целевой процесс: утверждение Романом → Telegram → HeyGen на ноутбуке

Уточнение пользователя от 2026-10-10. Ноутбук — **Windows**, подтверждено пользователем. Этот документ задаёт актуальную цель; прежний ручной экспорт HeyGen остаётся резервным способом, а не окончательной архитектурой.

Текущее ограничение: рядом с ноутбуком никого нет, настройка отложена. До его подключения используем обработчик **manual_upload** с тем же контрактом, позднее переключим ожидающие задания на **windows_browser**. [Реализованное ядро очереди и ограничения](AVATAR_PROVIDERS.md). Бот, transport и реальный worker ещё не развёрнуты.

## Пользовательский процесс

1. Gemini готовит сценарий и три варианта хука. Роману показывается весь предлагаемый текст и каждый хук, а не только название темы.
2. Роман утверждает точную ревизию сценария и выбранные хуки либо возвращает их на доработку. Нельзя считать утверждённым хук только потому, что утверждён основной текст.
3. После утверждения доступна кнопка **«Запустить производство» в Telegram-боте**. Она запускает задание или выбранный пакет, но не выдаёт разрешение на неутверждённые версии.
4. Worker на удалённом ноутбуке открывает HeyGen в обычном пользовательском интерфейсе, использует аватар Романа, вставляет точный утверждённый текст, запускает генерацию в согласованных пределах, ждёт результат и скачивает MP4. **HeyGen API не используется.**
5. MP4 попадает во входящую папку Google Drive с привязкой к версии/ревизии/хешу. Далее — проверка байтов, свежая расшифровка и совпадение речи, монтаж Remotion, проверки качества, загрузка готового ролика.
6. Бот сообщает состояние и ссылку на готовый результат. Публикация в Instagram автоматически в этот этап не включена.

Цель — убрать ручное копирование сценариев/заданий и запускать процесс кнопкой. Полная цепочка ещё не реализована и не проверена. Подтверждение текста и кнопка запуска — два разных события.

## Канал утверждения и личность

Текущее Google-утверждение — установленный пользователем промежуточный механизм; реальные разрешённый редактор/квитанция ещё требуют проверки. Для удобного целевого процесса можно показывать сценарий и хуки непосредственно в боте, сохраняя Sheets как журнал. Окончательное место утверждения (бот или Sheets с уведомлением в боте) ещё нужно подтвердить пользователю до смены действующего механизма.

Если утверждение происходит в Telegram, сервер проверяет постоянный Telegram user ID Романа, привязку callback к показанной версии и текущие хеши. Username/имя отправителя/текст callback сами по себе не удостоверяют автора. Ручная подстановка email Романа в существующий Apps Script receipt недопустима: событие Telegram должно иметь собственный подтверждённый канал и идентификатор автора.

Утверждение основы и каждого выбранного хука связывается с точной речью соответствующего ролика. Существующий контракт `scriptHash` включает version_id, revision, hook_text и полный script_text; менять эту семантику без миграции нельзя. Изменение текста или хука отзывает допуск. Для трёх вариантов не дублировать озвучку хука: pilot script_text уже содержит его в начале.

Кнопка запуска доступна только разрешённому оператору; кто именно кроме Романа может запускать пакет, ещё требуется настроить. Если в боте показан длинный сценарий несколькими сообщениями, решение связывается со всем пакетом текста, а не с первым фрагментом.

## Координатор и ноутбук

Координатор принимает Telegram update, проверяет запрос и автора, повторно читает утверждение, создаёт постоянное задание. Callback содержит короткий ID задания; токены/речь/команды shell в callback не помещаются. Telegram update_id/callback ID, job_key и атомарный захват исключают двойной запуск от повторной доставки или двойного нажатия.

Предпочтительная схема worker — исходящее получение ограниченного задания из очереди. Постоянный публичный удалённый shell/RDP не требуется. Удалённый доступ к ноутбуку нужен для первичной настройки, входа в HeyGen, диагностики и восстановления. ОС — Windows. Точный инструмент доступа, владелец ноутбука и расписание доступности пока не установлены. Требуется доступная пользовательская сессия Windows с браузером; реализацию worker проверить с учётом сна/блокировки и восстановления после перезагрузки.

Worker управляет браузером локально на ноутбуке, в отдельном пользовательском профиле. Вход/2FA подтверждает владелец аккаунта. Пароли, cookies, сессионные профили, OAuth и токены бота не передаются через чат и не коммитятся. CAPTCHA, повторный вход, неожиданное списание/изменение тарифа или изменившийся интерфейс переводят job в `needs_attention`, без обхода ограничений сервиса.

Действие создания в HeyGen может потреблять кредиты. Отсутствие API не делает генерацию бесплатной. До первого реального запуска подтвердить доступный план/кредиты, выбранный аватар, пределы пакета и право нажимать Generate. Кнопка запуска в дальнейшем действует в настроенных пользователем пределах. Текущая подготовка этого документа ничего не расходует.

Если после Generate пропала связь, сохранить ID/ссылку проекта и состояние, проверить уже созданный результат, не повторять создание вслепую. Браузерная автоматизация зависит от интерфейса и требует реального теста на ноутбуке; наличие remote desktop само по себе не доказывает её работоспособность.

## Состояния задания

`draft → awaiting_approval → approved → queued → avatar_running → avatar_ready → transcribing → ready_to_render → rendering → uploading → completed`.

Дополнительные состояния: `rejected`, `approval_revoked`, `needs_attention`, `failed`. Переход в queued возможен только по кнопке и после проверки точного утверждения. Между длительными этапами утверждение проверяется повторно. Отзыв во время генерации может не отменить уже потраченные кредиты, но блокирует выдачу результата как разрешённого и следующий этап.

Drive/Sheets являются хранилищем/журналом; одно изменение dropdown не заменяет атомарную очередь. Реализовано локальное SQLite-ядро постоянных заданий с атомарной вставкой и дедупликацией кнопок; coordinator ещё не развёрнут и lease для production-worker не реализован. Remotion может выполняться через GitHub Actions; кнопка Telegram должна обращаться к защищённому серверу координатора, а не давать пользователям GitHub credential.

## Что готово сейчас

- Существующая automation-ветка, draft generator Gemini, проверенный ранее render/upload статической композиции.
- Exact-text manifests, metadata-only intake planner и offline-проверки; производство ими не запускается.
- Дополнение Apps Script установлено по действиям пользователя; личное утверждение ещё ожидается.
- Три новых пилота в Google pending; никакой роли боту по подмене решения Романа нет.
- Задание Claude Code для монтажа цельного MP4 и выключенный headless runner с предложением patch. OAuth runner пока не настроен.

## Что осталось построить

1. Подтвердить ноутбук/ОС/доступ; отдельные бот и разрешённые Telegram IDs; место утверждения; право запуска и лимиты пакета.
2. Реализовать Telegram-координатор, хранение решений/снимков и постоянную очередь с dry-run кнопкой без генерации.
3. Настроить локальный worker ноутбука и провести безопасную проверку входа/выбора аватара без Generate. Затем согласовать один реальный ролик.
4. Соединить результат HeyGen с Drive, настоящей расшифровкой, новым Remotion-компонентом и QC. Сохранить блокировки текущего intake до успешных проверок.
5. Проверить повторное нажатие, повторную доставку update, офлайн ноутбук, потерю связи после Generate, изменение текста/хука и возврат после ошибки. Только затем согласовывать масштаб 30 тем × 3 ролика.

Claude Code разрабатывает компоненты; Codex проверяет контракт, изменения и тесты. Нельзя запускать две реализации одной очереди независимо или переписывать чужие коммиты.
