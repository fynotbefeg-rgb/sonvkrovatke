# Выбор темы до написания основы и хуков

Разработка в feature/codex-pipeline, 2026-10-12. **В Google не установлено.** Живой Version 4 пока поддерживает прежние shared packets и выключенный snapshot, а не этот новый action.

## Поведение

Аутентифицированный `add_topic_review` получает packet по schemas/topic-only-review-v1.schema.json: schemaVersion, topicId, topicText, revision, analysis, statistics, referenceUrl. Основа и хуки отсутствуют, фиктивный сценарий не создаётся. Лимит 8000 UTF-8 байт, максимум 90 текущих topic-only регистраций; реальная общая квота Script Properties может ограничить число больших packets раньше, и запись тогда должна остановиться с ошибкой.

В существующем листе «Темы и хуки» добавляется одна строка из семи колонок: A тема; B решение; C/D пустые до текста; E анализ; F статистика; G ссылка. Новые колонки/вкладки не нужны, существующие строки не удаляются и не перезаписываются. При повторе того же packet строка не добавляется. Новая ревизия добавляет историю, сбрасывает выбор и запрещает прежнюю speech-версию.

Выбор принимается только при настоящем одиночном edit в B от разрешённого e.user. Видимый dropdown без серверной квитанции, bulk-edit, другой лист/аккаунт, формула, изменённая тема, вставка основы в topic-only строку и будущая дата не дают выбор. Анализ/статистика/ссылка не являются speech approval и их изменение не меняет hash темы. Их точность и свежесть нужно проверять отдельно до показа Роману; схема сама не доказывает популярность ролика.

Тема появляется в существующем authenticated get_topic_research_snapshot. Контракт snapshot v1 не меняется: domain hash shared-review-v1, статус selected_for_research, никаких текстов речи и productionAllowed=false. Название source apps_script_shared_review сохранено как совместимость модуля. Выключенный snapshot по-прежнему enabled=false/topics=[].

## Переход к основе и трём хукам

После исследовательской проверки и редакционного контроля оператор может отправить обычный add_shared_review с тем же topicId, точным topicText и revision выбранной темы. Модуль повторно проверяет живую доверенную квитанцию, добавляет обычный блок из четырёх строк и сохраняет **только** исходную квитанцию этой же темы: неизменные hash/approvedBy/approvedAt. Тексты основы, хуков и окончаний не утверждаются автоматически. Их решения нужны отдельно. Историческая строка выбора темы остаётся; её отказ/изменение немедленно блокирует и связанную production queue.

При замене ревизии сценария текущая схема требует согласованной новой topic revision; независимое версионирование темы/речи — дальнейшее изменение контракта, не заявляется реализованным. Существующие full-shared темы автоматически в topic-only не переводятся: новая регистрация такого ID отклоняется, чтобы не импортировать старые решения. Миграция действующих строк — отдельная проверяемая операция.

Все legacy receipts для topicId и его instagram/tiktok вариантов исключаются из очереди, если ID управляется topic-only. Выбранная тема сама по себе никогда не может запускать HeyGen/рендер. При выключении флага managed темы не возвращаются в legacy очередь. ProductionQueue продолжает получать прежний точный контракт после всех действительных утверждений.

## Тесты и установка

topic-only-review.test.mjs: 14 новых регрессий + 10 импортированных базовых. Проверены доверенное чтение без сценария, отказ/подмена/ревизии, повторы/частичная запись, legacy обходы, переход к speech с сохранением первоначальной квитанции и отдельным утверждением текстов, generated addon, сохранение unrelated legacy approvals и повреждённые bindings. Старые shared/reader тесты тоже обязательны. Схема и байтовый лимит не заменяют проверку фактов.

Обновление включает SharedReview.gs и generated RomanApproval.gs; живой legacy Code.gs остаётся неизменным. Сначала сделать приватный backup текущего Version 4, сравнить его с применёнными хешами PR17 и подготовить проверяемый кандидат/откат. Установку, новую версию существующего deployment, включение флага и регистрацию реальных строк не делать в рамках локальных тестов. Не удалять старые файлы/квитанции, не открывать секреты в browser snapshots. Для настоящего e.user теста понадобится решение разрешённого редактора; не подменять его владельцем или программным setValue.

Не реализованы автоматически: запуск Apify после выбора, семантическая проверка видео, Gemini drafting worker и дальнейший production end-to-end. Не считать этот модуль всей фабрикой. SEO-тема Романом пока не утверждена.
