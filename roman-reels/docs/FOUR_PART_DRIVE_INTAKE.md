# Приём трёх хуков и общей основы

2026-10-12. Облачный код приёмщика теперь поддерживает отдельный четырёхчастный
пакет. Старый шестичастный режим остаётся обязательным для своих пакетов:
отсутствующие окончания не переключают режим автоматически.

## Точное подключение

Используются существующие `drive_intake.scan`, single-writer журнал и Drive API.
Пакет передаётся явно доверенным вызывающим кодом, а не обнаруживается по именам
произвольных файлов или по заголовку HeyGen. Для четырёхчастного пакета:

- `draftVersion: "3.0.0"`, `mode: "editorial"`, `productionReady: false`;
- `sourceSet`: `topic_id`, `recordingParts: 4`, `status: "pending_approval"`,
  точные `body_text`, его SHA-256 в `body_text_hash`, три `hooks`
  с `hook_id` 1/2/3 и точными `hook_text`; окончания отсутствуют;
- `items`: ровно три полных варианта `R-<topic>-h<1|2|3>`,
  `topic_id`, `hook_id`, единая `script_revision` 1..9999,
  `hook_text`, `script_text = hook + '\n\n' + body`,
  `script_hash` по существующему `legacy_hash`, `status: pending_approval`;
- папка `<topic>/v<revision>`: `hook-1.mp4`, `hook-2.mp4`, `hook-3.mp4`,
  `body.mp4`, `recording-set.json`.

Квитанция сохраняет существующий формат `receiptVersion: "1.0.0"`,
`topicId`, `scriptVersion`, `files` с четырьмя точными `fileName`, `sha256`,
`textHash`. Она заявляет привязку записи к тексту, но не доказывает совпадение
произнесённых слов и не является утверждением Романа.

Загрузчик PR22 пока передаёт только MP4. Без квитанции комплект ожидает
`recording-set.json` без скачивания больших файлов. Генератор квитанции,
динамический реестр актуальных пакетов и их доставка облачному запуску ещё
не подключены. Не использовать старый отклонённый текст для их заполнения.

После проверки квитанции, SHA/MD5/метаданных и полного декодирования приёмщик
создаёт совместимый план `assemblyVersion: "1.0.0"` для существующего сборщика.
При скачивании четыре SHA и четыре textHash сохраняются в постоянный журнал;
повторный запуск не принимает их за неполный шестичастный комплект.

Три точных актуальных утверждения проверяются тем же authenticated reader;
отзыв любого понижает готовность. `renderAllowed` всегда false: дальнейший
исполнитель заново проверяет утверждение, получает реальные байты файлов,
собирает видео и проверяет речь перед рендером.

## Что реально проверено

Новая suite использует реальные синтетические MP4 и fake Drive: четыре части
и квитанция, перезапуск без повторного скачивания, неполные/отозванные
утверждения, отсутствие квитанции, запрещённый fallback, неверный текст,
изменение удалённого файла, synthetic gate, совместимость с существующим
сборщиком. Настоящие Google/HeyGen и платные вызовы не используются.

PR22 отдельно подтверждает одну настоящую загрузку `hook-1.mp4` и повтор с тем
же file ID. Это не проверка полного четырёхчастного облачного приёма.

Расписание и его действующий список шестичастных пакетов не изменены.
Четырёхчастный режим подготовлен в коде; он не включён для реальных тем,
новый монтаж/загрузка готового MP4 ещё не выполнялись.

## Генератор квитанции из локального журнала загрузчика

`build-four-part-receipt.mjs` — автономный Node CLI, без OAuth/Google/HeyGen:

```text
node scripts/build-four-part-receipt.mjs packet.json journal-v1.json NEW-recording-set.json
```

Входы — явный четырёхчастный пакет выше и отдельный журнал PR22. Требуются
ровно четыре `uploaded` записи целевой темы/версии, уникальные Drive ID,
точные роли/имена и ненулевые размеры/SHA. Каждая запись уже должна иметь
`textHash`, назначенный из точного текста в исходном задании ДО загрузки.
Он не добавляется задним числом. Старый тест h1 без textHash намеренно не
может сформировать такую квитанцию. Никакие утверждения не создаются.

Выход содержит только существующие поля receipt v1; запись эксклюзивная,
исходные пакет/журнал не меняются. Журнал не доказывает содержимое Drive:
облачный приёмщик всё равно скачивает и независимо проверяет SHA/MD5/текстовые
хеши/метаданные/decode; распознанную речь нужно сверять отдельно.

Пять автономных тестов проверяют точное соответствие Python ожиданиям,
отсутствующий textHash, неполный/неоднозначный/чужой revision, изменённую речь,
отсутствие перезаписи квитанции и изменения журнала. Межъязыковая проверка
исполняется в облачной CI с Python; Python для Windows-загрузчика не нужен.

Этот CLI пока не встроен в Windows-загрузчик и НЕ загружает JSON на Drive.
Следующее задание Claude: использовать функцию после четырёх проверенных
загрузок, затем отдельно передать квитанцию с проверкой контрольной суммы
и повторного запуска; не включать реальное производство/автозапуск.

## Явная передача пакета облачному запуску

`run-drive-intake.py --packets /path/to/packets.json` принимает один пакет или
массив из 1..30 пакетов. Размер ограничен 2 МиБ, повтор одной темы/версии,
неверные хеши/варианты и строковые вместо boolean synthetic-флаги отклоняются
до чтения credentials/сети. Старый запуск без аргумента читает прежний реестр.
Флаг старого шестичастного self-test несовместим с новым аргументом.

Это вход доверенного оператора/worker, не приём произвольной ссылки от клиента:
CLI не создаёт сценарии, не доказывает выбор темы или авторство утверждения.
Тот же fresh authenticated approval reader остаётся обязателен. Workflow и
расписание пока не передают этот аргумент: живой четырёхчастный scan не включён.

Дополнительная интеграционная проверка создаёт квитанцию именно Node-функцией
по журналу fake uploader с SHA реальных синтетических MP4, затем скачивает
и полностью проверяет комплект Python-приёмщиком. Это сквозная локальная
проверка двух языков и файлов; реальный Drive здесь не используется.

`check-four-part-drive-fixture.py` жёстко привязан к пакету
windows-receipt-test-20261012/v1 и SHA-256
`e9524729a2103ef2211d1eb79cf886d74a83f02d78dacf250fbad805845263c3`.

проверку; не нормализовать этот файл без осознанной смены fixture pin.

Ручной workflow roman-reels-check в feature/codex-four-part-intake:
включить только four_part_drive_self_test и check_drive_intake_access.
Остальные опции false. Новый job использует existing service-account credential
с OAuth scope drive.readonly; клиент обёрнут интерфейсом без операций записи.
Локальный временный журнал нужен только для проверки существующего scan;
общий intake-state не читается/не меняется. Нет approval/LLM/HeyGen/рендера.

Успех = downloadedSets1, четыре SHA/textHash, полный decode, awaiting_approval,
renderAllowed=false. Report в Actions artifact на три дня, без токенов и текстов.
Это реальное облачное чтение тестового комплекта, не включение scheduled
приёмки, не проверка речи и не новый production-job.
