# План открытия двух кандидатов для Романа — без живого включения

Основа: TOPIC_FIRST_REVIEW.md и текущие SharedReview.gs/RomanApproval.gs. Старые пометки о Version 4
в прежнем документе исторические: по переданному владельцем отчёту установлен Version 6. Это не
повторная независимая проверка живого Google-проекта. Этот PR меняет только документацию.

Ничего не включено и не отправлено: флаг, файлы Apps Script, deployment, строки, квитанции, триггеры,
права доступа, бот и очередь остаются прежними. Реальный выбор делает только Роман.

## Что потребуется после отдельного разрешения владельца

- Флаг `ROMAN_SHARED_REVIEW_ENABLED`: изменить прежнее отсутствующее/false значение на точную строку
  `true` лишь после предварительных проверок. Это общий флаг модуля, **не** отдельный режим «только
  смотреть»: он также открывает регистрацию и проверку managed-согласований. Возможное влияние на
  ранее зарегистрированные темы нужно проверить; `enabled=false/topics=0` не доказывает пустой реестр.
- Две новые регистрации через защищённый POST `action=add_topic_review`, существующий токен используется
  только через уже разрешённый локальный доступ. Не создавать новый токен и не читать его из браузера,
  GitHub, Script Properties или резервных копий. Не выполнять `add_shared_review` на этом этапе.
- Существующие `ROMAN_APPROVER_EMAILS`, редакторский доступ Романа к таблице и установленный обработчик
  `onRomanApprovalEdit` должны обеспечивать его личный одиночный edit с настоящим `e.user`. Никакие
  изменения allowlist, sharing или триггеров не входят автоматически в разрешение на просмотр.
  Текущий allowlist глобальный: если он допускает других утверждающих, технической гарантии «только
  Роман» для этих тем нет. Остановиться и согласовать ограничение отдельно, не менять глобальный список
  молча и не ломать старые согласования. Если `e.user` недоступен, не подменять его владельцем/setValue.

## Предварительные проверки — до флага и записей

1. Сверить текущий локальный каталог с ожидаемым SHA из ROMAN_TOPIC_REVIEW_MESSAGE.md. Проверить два
   названия, публичные ссылки, false-флаги и `awaiting_roman_review`. Каталог — редакционная подсказка,
   не источник утверждений; его JSON и локальные пути не переносить в Git.
2. Приватно сохранить свежий backup живых Code.gs/RomanApproval.gs/SharedReview.gs, текущую версию
   deployment, настройки execute-as/access, прежнее точное состояние флага и затрагиваемые привязки.
   Сравнить исходники с ожидаемым установленным V6. Не выводить Script Properties целиком, секреты,
   URL webhook или квитанции в отчёт. Не использовать старый Version 4 как текущую базу.
3. Через существующий защищённый доступ прочитать `get_review_status_snapshot`,
   `get_topic_research_snapshot` и `get_production_queue`: записать лишь enabled/количества/false-флаги.
   Ожидаемое последнее состояние — просмотр выключен, очередь 0; при расхождении остановиться.
4. Подтвердить реестр и отсутствие коллизий предложенных IDs через целевые приватные привязки, без
   чтения/переноса секретов. Полный список скрыт выключенным snapshot; если безопасно проверить реестр
   нельзя, включение блокируется до согласованного способа проверки. Не обходить это временным флагом.
   Новые IDs ниже не должны совпадать с существующими full-shared/legacy темами или импортировать их
   исторические отметки. Code.gs не менять, новый deployment по умолчанию не нужен, setup не запускать.
5. Запустить локально topic-only-review.test.mjs, shared-review.test.mjs, review-status.test.mjs,
   disabled-topic-snapshot.test.mjs, topic-selection-reader.test.mjs и approved-four-part-jobs.test.mjs, зарегистрированные в CI. Уточнить актуальные публичные сведения о референсах либо явно
   оставить статистику неизвестной. Не заявлять «залетел», текущие просмотры, бесплатность инструментов
   или результат для сайта без проверки. В этом PR новых исследований/API-вызовов нет.

## Две регистрации, только после разрешения и пройденных проверок

Каждый packet содержит **ровно** `schemaVersion`, `topicId`, `topicText`, `revision`, `analysis`,
`statistics`, `referenceUrl`, по topic-only-review-v1.schema.json, не более 8000 UTF-8 байт. Никаких
bodyText/hooks, полей approved/approved_by/receipt или фиктивного сценария. `revision=1` для свежего ID.

| Кандидат локального каталога | Предложенный свежий topicId | topicText / referenceUrl |
|---|---|---|
| ai-seo-audit | roman-topic-seo-20261013 | Точное полное название из каталога / DZm25XXMZ4I |
| ai-cross-platform-content | roman-topic-content-20261013 | Точное полное название из каталога / DeHPwcrhmy4 |

`analysis`: конкретная бизнес-задача из каталога, а не обещание эффективности. `statistics`: честное
«Текущие счётчики и бесплатность показанного решения не перепроверены». `referenceUrl`: полная публичная
HTTPS-ссылка из каталога. Непустые буквальные строки, без формул. Свежие IDs — предложение, не уже созданные
регистрации; при коллизии остановиться и подготовить новое соответствие, не мигрировать старые решения.

Последовательность:
1. Сохранить прежнее значение флага, затем установить `true`.
2. Сразу проверить снимки и очередь против предварительного реестра и baseline. При неожиданном
   появлении утверждений/заданий отключить флаг и разбирать состояние; ничего не запускать.
3. Отправить два `add_topic_review` по одному. Записать фактические `firstRow`, `added`, `rows`,
   `approvalGranted=false` и проверить readback. A — точная тема; B/C/D пустые; E анализ; F ограничения;
   G ссылка. Другие строки, формулы, decisions, источники и квитанции должны остаться прежними.
4. При потере ответа сначала проверить сохранённую привязку/строку. Повтор **того же** packet допустим
   только после сверки и должен дать `added=false`; частичную запись не удалять и не исправлять вслепую.
5. Проверить `get_review_status_snapshot`: ровно две ожидаемые новые topic-only записи с topic=pending,
   body/hook1/hook2/hook3=not_created и `approvalWrites/productionAllowed=false`. Другие registrations
   должны совпадать с предварительным реестром; не обещать общее topics=2, если в нём есть другие записи.
   `get_topic_research_snapshot` пока не содержит выбранных новых тем; production queue остаётся baseline 0.
6. Только теперь дать Роману сообщение, ссылку и фактические номера новых строк. Ему не нужно входить в
   GitHub или операторский Telegram-бот. Ответ «выбрал» в чате — обратная связь, не серверная квитанция.

## Проверка личного выбора и переход к текстам

Роман со своего разрешённого аккаунта меняет одну ячейку B новой строки на «Утверждено». Оператор ничего
не утверждает за него. После настоящего edit проверить trusted topic receipt: правильные ID/revision,
domain hash `shared-review-v1`, его allowlisted actor и не будущая дата. Не выдавать dropdown без квитанции
за выбор. Отчёт без email/хешей/секретов; отсутствие `e.user` — блокер, не повод программно заполнить ячейку.

Выбранная тема появляется в snapshot как `selected_for_research`. Основа/хуки остаются not_created,
production queue 0. Это разрешает следующий редакционный этап, **не** производство. После исследования
и подготовки реальных текстов — отдельный `add_shared_review` с теми же topicId/topicText/revision:
переносится только прежняя доверенная квитанция темы, основа и три хука должны утверждаться отдельно.
Ни Gemini, ни Claude не делают эти утверждения. У этого этапа генерация Gemini также не разрешена.

## Откат без удаления доказательств

- Вернуть точное прежнее состояние `ROMAN_SHARED_REVIEW_ENABLED` (false или отсутствие ключа, как было).
  Проверить disabled snapshots и очередь против baseline; не считать это удалением новых registrations.
- Новые строки, registrations, квитанции и backup оставить. Не стирать их и не возвращать старые
  «Утверждено». Managed-темы при выключении не должны проходить через legacy-очередь.
- Так как код/deployment не меняются, их откат не требуется. Если предварительная сверка обнаружит
  необходимость менять код, создать отдельный кандидат и разрешение, с откатом к реально текущему V6,
  а не выполнять такую установку под видом открытия просмотра.
- Бот, задача супервизора, DPAPI-конфиги, SQLite, курсор, HeyGen, загрузки видео, монтаж и производство
  остаются нетронутыми. Никаких сообщений Роману этим PR не отправлено.
