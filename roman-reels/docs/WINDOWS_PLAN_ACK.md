# Подтверждение получения заданий ноутбуком — кандидат

2026-10-13. Код и автономные тесты. Живой Drive, бот, Google, автозапуск, HeyGen и производство не менялись.
Основа: `windows-plan-delivery.mjs` / `receive-windows-plan.mjs` (WINDOWS_PLAN_DELIVERY.md).

## Контракт

Подтверждение означает только «этот точный пакет сохранён и перепроверен на Windows». Оно **не** является
утверждением, разрешением загрузки, генерации аватара, монтажа или рендера: все флаги false,
`currentApprovalRecheckRequired: true`.

```json
{"ackVersion":"1.0.0","status":"received","deliveryId":"<sha256 payload>","contentSha256":"<sha256 байтов конверта>",
 "topicId":"…","scriptVersion":1,"planKey":"<64 hex>","jobCount":4,"issuedAt":0,"expiresAt":0,"receivedAt":0,
 "generationAllowed":false,"uploadAllowed":false,"renderAllowed":false,"currentApprovalRecheckRequired":true}
```

- Привязка: `deliveryId` (хеш payload), `contentSha256` (хеш точных байтов прочитанного конверта, т. е. и срока),
  `planKey`, `expiresAt`. Подтверждение старого конверта не покрывает продлённый конверт того же плана.
- Создаётся только в `afterVerified` под `receive.lock`: после записи всех файлов, rename и повторного чтения
  каждого файла с диска (`verifyStaged`, теперь вызывается и для нового, и для повторного приёма).
- Просроченный (в том числе истёкший между сохранением и подтверждением), повреждённый, изменённый на диске
  или из чужого/неверно настроенного слота пакет не подтверждается.

## Хранилища (отдельные от облачного журнала приёмщика)

1. Локально: `%LOCALAPPDATA%\RomanReels\source-uploader\delivery-acks\<deliveryId>.<contentSha256>.json`.
   Запись через временный файл + `fsync` + эксклюзивный hard link. Повтор и перезапуск переиспользуют те же байты
   (тот же `receivedAt`), второй записи нет.
2. Drive: один закреплённый файл `source-plan-ack-v1.json` рядом с почтовым ящиком в `_windows-jobs`, начальное
   содержимое `{"ackVersion":"1.0.0","status":"empty"}`. Windows обновляет только его байты (PATCH по ID, без
   создания файлов). Перед записью проверяются ID/имя/MIME/родитель/размер/MD5; одинаковые байты — без записи;
   чужое содержимое не перезаписывается; после записи — метаданные и readback.
   После потерянного ответа следующий запуск сначала читает слот, поэтому дубликатов нет.

`intake-state` облачного приёмщика, почтовый ящик `source-plan-v1.json` и загрузчик не меняются.

## Координатор

`mayReplaceDelivery({currentBytes, ackBytes, nextBytes})`: пустой ящик или продление того же плана — можно;
другой план — только если `isAcknowledged(current, ack)` для точных текущих байтов. Иначе
`previous_not_acknowledged`. Нынешний `publish-windows-plan.py` по-прежнему блокирует любой другой план;
подключение этой проверки к издателю (чтение слота сервисным аккаунтом) — отдельный следующий шаг.

## Запуск после настройки (не выполнялся)

Владелец создаёт `source-plan-ack-v1.json` с пустым содержимым в `_windows-jobs`; сервисному аккаунту — только
чтение. На Windows — локальный `delivery-ack-config.json` вида `{"fileId":"…"}` вне Git. Затем из `roman-reels`:
`node scripts/ack-windows-plan.mjs` (один опрос, без аргументов).
